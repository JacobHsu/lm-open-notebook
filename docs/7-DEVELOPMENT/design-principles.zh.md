## 🎨 UI/UX 原則

### 專注於內容,而非介面裝飾

- 減少 UI 雜訊與干擾
- 內容應占據螢幕的大部分空間
- 控制項只在需要時出現,而非一直顯示
- 不同檢視畫面之間維持一致的版面配置

### 漸進式揭露

- 先顯示簡單選項,進階選項按需顯示
- 不要用所有可能的設定淹沒新使用者
- 提供適用於 80% 使用情境的合理預設值
- 讓進階功能可被發現,但不強加於使用者

### 反應迅速

- 常見操作的 UI 應該感覺是即時的
- 對耗時的操作顯示載入狀態
- 盡可能快取與最佳化
- 在慢速連線下也能優雅降級

## 🔧 技術原則

### 清楚的關注點分離

**各層不應互相滲透**:
- 前端不應該知道資料庫結構
- API 不應包含商業邏輯(應委派給領域層)
- 領域模型不應該知道 HTTP 請求
- 資料庫層不應該知道 AI 供應商

### 型別安全與驗證

**及早捕捉錯誤**:
- 所有 API 邊界使用 Pydantic 模型
- 整個 Python 程式碼庫使用型別提示
- 前端程式碼使用 TypeScript
- 在系統邊界驗證資料

### 測試真正重要的東西

**聚焦於有價值的測試**:
- 測試商業邏輯與領域模型
- 測試 API 合約與錯誤處理
- 不要測試框架程式碼(FastAPI、React 等)
- 對關鍵工作流程進行整合測試

### 資料庫作為單一事實來源

**SurrealDB 是我們唯一的事實來源**:
- 所有狀態都持久化在資料庫中
- 資料庫層不包含商業邏輯
- 適當使用 SurrealDB 的功能(記錄連結、查詢)
- 所有結構變更都透過 schema 遷移進行

## 🚫 應避免的反模式

### 功能蔓延(Feature Creep)

**表現形式**:
- 因為「很酷」或「很簡單」就新增功能
- 在常見情境還沒做好之前,就先為邊緣案例建構功能
- 試圖滿足所有人的所有需求

**應該這樣做**:聚焦於核心使用情境;對不符合[願景](../../VISION.md)的功能說不;為邊緣案例建立可擴充的接點。

### 過早最佳化

**表現形式**:
- 在還不知道是否真的慢之前就最佳化程式碼
- 沒有實際量測影響就採用複雜的快取策略
- 為了微小的效能提升而犧牲程式碼清晰度

**應該這樣做**:先量測,再最佳化;聚焦於演算法層面的改進;在做效能調整之前先做剖析(profile)。

### 過度工程

**表現形式**:
- 為了「以後可能會用到」而建構抽象層
- 為三行程式碼的函式套用設計模式
- 打造框架,而不是解決問題

**應該這樣做**:從簡單開始,等模式浮現後再重構;以可讀性為最佳化目標;只在能簡化問題時使用抽象化,而非讓問題更複雜。

### 沒有遷移路徑的破壞性變更

**表現形式**:
- 變更資料庫結構卻沒有提供遷移腳本
- 修改 API 合約卻沒有版本管理
- 移除功能卻沒有提供棄用警告

**應該這樣做**:結構變更務必提供遷移腳本;先棄用再移除;清楚記錄破壞性變更。

## 🤝 決策框架

在評估新功能或變更時,請自問:

### 1. 是否符合我們的願景?
- 是否有助於使用者掌控自己的研究資料?
- 是否支持隱私與自架部署?
- 是否符合我們的核心使用情境?(參見 [VISION.md](../../VISION.md))

### 2. 是否遵循我們的原則?
- 使用與理解是否簡單?
- 是否可透過 API 運作?
- 是否支援多個供應商?
- 使用者是否能擴充它?

### 3. 實作是否穩健?
- 是否維持關注點分離?
- 型別與驗證是否正確?
- 是否包含測試?
- 是否有文件說明?

### 4. 成本是什麼?
- 這會增加多少複雜度?
- 維護負擔有多大?
- 是否引入新的依賴項?
- 使用頻率是否足以證明這個成本是值得的?

### 5. 是否有其他替代方案?
- 現有功能能否解決這個問題?
- 這能否以外掛或擴充套件的形式建構?
- 這是否應該是一個獨立的工具?

**當一項決策解決了結構性問題**——不論是架構還是產品層面——請在同一個 PR 中將其記錄為
[決策紀錄](decisions/README.md)。趁脈絡還新鮮時,寫下半頁就好。

## 給貢獻者的話

在提出功能或變更建議時:

1. **參照願景與原則**——說明你的提案如何符合 [VISION.md](../../VISION.md)
2. **指出取捨**——誠實說明你用什麼換取什麼
3. **提出替代方案**——展現你已考慮過其他做法
4. **樂於接受回饋**——維護者可能會看到你沒注意到的疑慮

**請記得**:功能被拒絕不代表對你或你的想法的評判。這只是代表我們要專注於核心願景。我們感謝所有的貢獻與想法!
