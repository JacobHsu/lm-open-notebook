## Discussion 管理

Discussions 是功能請求、想法、行為變更、產品方向、設計、架構與貢獻提案的
受理與討論空間。一個被接受的想法,只有在足夠明確、可被追蹤與執行時,才會
變成一個 Issue。

### 當有新的 Idea Discussion 被建立

**1. 初步分流**(盡量在 24-48 小時內完成)

- 確認這是一個想法或開放式提案,而不是可重現的錯誤。
- 在 Discussions、Issues、PRs、`VISION.md` 與決策紀錄中搜尋相關脈絡。
- 當主題已經存在時,將訊號合併進正式的 Discussion 中;保留原作者與貢獻的連結。
- 當問題在於「是否/為什麼」該專案要推進此事時,將 `needs-triage` 換成 `needs-vision`;當問題是想要,但「怎麼做」尚未明確時,換成 `needs-design`。

**2. 形塑討論**

預設先詢問缺少的證據,而不是實作計畫:

- 使用者想要達成什麼?
- 現在有什麼困難?他們是怎麼變通的?
- 還有誰有相同的使用情境?
- 有哪些限制、替代方案或失敗模式很重要?
- 我們要如何驗證結果變得更好?

對於較大型的提案,在 Discussion 內文或維護者留言中保留一份綜整摘要:
已知什麼、還有什麼未定、有哪些替代方案,以及決策由誰負責。

**3. 收尾**

每個成熟的 Discussion 最終都要有明確的結果:

- **已接受:**從該 Discussion 建立一個或多個範圍明確的 Issue,將繼承的探索類標籤換成 `ready`,雙向連結,並將 Discussion 標記為已解決並關閉。
- **實驗:**描述限定範圍的實驗內容,以及做出承諾前需要的證據。
- **暫緩:**說明現在為什麼不是時機,以及什麼條件會讓它重新開啟。
- **拒絕:**說明與願景、範圍或維護成本的衝突之處。
- **取代/重複:**連結到正式的 Discussion 或倡議。

建立 Issue 是「畢業」的事件:代表專案已承諾追蹤可執行的工作,而不只是
這個想法獲得了正面反應。

## Issue 管理

### 當有新的 Issue 被建立

**1. 初步分流**(盡量在 24-48 小時內完成)

- 公開的 Issue 會透過錯誤或安裝表單進來,並帶有 `needs-triage` 標籤。
- 當已接受的 Discussion 畢業成為可執行的工作時,維護者也會建立 Issue。
- 在適用時加上一個**類型(type)**標籤與一個**領域(area)**標籤(見[標籤](#標籤))。

快速評估:

- 這是一個可重現的錯誤,還是一個已核准的工作項目?
- 這是否與既有的 Issue 重複?
- 是否需要更多重現細節或環境資訊?
- 如果這是一個想法、功能請求或開放式提案,將它轉為 Discussion,並說明流程。

**2. 初步回應**

```markdown
感謝你開啟這個 issue!我們會盡快審查並回覆你。

[如果是錯誤回報] 在等待的同時,你是否已經查看過我們的疑難排解指南?
```

**3. 錯誤分流**

自問以下問題:

- 能不能依提供的步驟與環境重現?
- 是否需要回報者提供更多資訊?
- 是否已經修好了、是重複的,還是源自上游相依套件?
- 預期行為其實是不是一個產品/設計決策?如果是,先開啟或連結一個 Discussion,再定義修法。

**4. Issue 指派**

如果貢獻者勾選了「I am a developer and would like to work on this」:

**針對已分流的 Issue:**

```markdown
感謝你這麼清楚的回報。我們已確認這是專案應該追蹤的工作。

我看到你想認領這個工作。在你開始之前:

1. 請分享你提議的做法/解法
2. 閱讀我們的[貢獻指南](contributing.zh.md)與 [VISION.md](../../VISION.md)
3. 一旦我們對做法達成共識,我就會把這個 issue 指派給你

期待你的想法!
```

**針對需要澄清的 Issue:**

```markdown
感謝你主動提出想認領這個工作!在我們繼續之前,有幾件事需要先釐清:

1. [問題 1]
2. [問題 2]

拿到這些細節後,我們就可以討論最好的做法。
```

**針對被開成 Issue 的想法:**

```markdown
感謝你的提案!我們使用 GitHub Discussions 來處理功能請求、
產品/設計/架構想法,以及貢獻提案,讓社群能在它們變成實作承諾之前先加以探討。

我要把這個 Issue 轉換成 Discussion。如果方向被接受且範圍夠明確,
我們會在實作之前,從中建立一個已核准的 Issue。
```

### 標籤

標籤集合是經過整理的——**不要自行發明標籤**。如果有不合適的情況,提出來討論,而不是自己加一個。在適用時各指派**一個狀態(state)**、**一個類型(type)**與**一個領域(area)**;多個組合/生態系標籤則沒問題。

**探索狀態**——主要用在 Discussions 上。歷史遺留的 Issue 在待整理期間可能
仍保留這些標籤;請勿再將新的功能提案導入 Issues:

| 標籤 | 意義 |
|---|---|
| `needs-triage` | 新訊號,尚未分類 |
| `needs-vision` | 不確定是否/如何適合本專案——需要維護者做策略判斷(對照 [VISION.md](../../VISION.md)) |
| `needs-design` | 想要,但「怎麼做」尚未定案——需要先有設計/規格才算就緒 |

**Issue 執行狀態:**

| 標籤 | 意義 |
|---|---|
| `needs-triage` | 新的錯誤或安裝回報,尚未分流 |
| `needs-info` | 等待回報者確認或提供更多資訊 |
| `ready` | 已核准且描述充分——開發流程可以接手 |
| **關閉(Close)** | 使用 GitHub 原生的關閉理由(重複/不予處理);重複/被取代時要連結到正式的 issue |

**類型(Type)**——是哪一種工作(明確時指派一個):
- `bug` · `enhancement` · `documentation`
- `installation` 是由 Issue 建立流程套用的受理標籤(而非分流時套用);安裝相關的回報會被導向 `area: deploy`。

**領域(Area)**——系統的哪個部分(一律套用,每個 Issue 一個):

| 標籤 | 適用範圍 |
|---|---|
| `area: chat` | 對話/聊天、RAG 檢索、代理式回應、引用 |
| `area: search` | 全文與語意搜尋 |
| `area: sources` | 來源擷取與處理(URL、檔案、擷取、分塊) |
| `area: notebooks` | Notebook 功能:筆記、洞察、轉換 |
| `area: providers` | AI 供應商整合 + 模型設定 |
| `area: embeddings` | Embedding 模型、向量化、語意索引 |
| `area: podcast` | Podcast/音訊生成 |
| `area: database` | SurrealDB、持久化、schema、遷移 |
| `area: ui` | 前端(Next.js)、UX、視覺相關問題 |
| `area: deploy` | Docker、部署、k8s、反向代理、基礎設施/安裝 |
| `area: offline` | 離線(air-gapped)運作 |
| `area: i18n` | 國際化/在地化 |

**組合/史詩(epics):**
- `umbrella` — 用於彙整相關工作的追蹤 Issue
- `tracked-in-umbrella` — 被某個 umbrella 涵蓋;請追蹤該 umbrella 以掌握進度
- `bundled` — 屬於某個主題性組合的一部分
- `upstream` — 根本原因出在我們的某個函式庫,而非這個儲存庫

**生態系(Ecosystem)**——真正歸屬於上游函式庫的 Issue:
- `esperanto`(模型抽象層) · `content-core`(內容擷取) · `podcast-creator`(Podcast 生成)

**社群:**
- `good first issue` — 小型、範圍明確、適合新人上手
- `help wanted` — 我們歡迎貢獻者接手

### 整合:Discussion 還是 umbrella?

當多個開放中的 Issue 都圍繞同一個主題時,依**這件事的決策程度**來挑選模式——而不只是看主題是否相同:

- **尚未有願景/設計定案的主題** → 建立或選定**一個正式的 Discussion**,在其綜整摘要中記錄每個請求的訊號(👍 數、感興趣的貢獻者),並將相關的 Issue 或 Discussion 轉換/連結過去。一個主題不是 N 個工作項目——而是一個共同的思考空間。
- **已經拆解成真正可平行進行的任務** → 使用 `umbrella` + `tracked-in-umbrella`。子項目維持開放狀態,因為每一個都可以獨立被認領(例如多使用者的 umbrella #712)。

經驗法則:如果工作要等**我們**做出決定才能開始,它屬於 Discussion。如果決定已經做出,且工作已拆分成貢獻者今天就能認領的項目,它屬於帶有子 Issue 的 umbrella。**絕對不要在未與現有的受指派人/貢獻者或開放中的 PR 協調的情況下,轉換或關閉該 Issue**——改用連結標記為某個階段即可。

## Pull Request 審查

### 初步 PR 審查檢查清單

**在深入程式碼之前:**

- [ ] 是否有對應的已核准 Issue?
- [ ] PR 是否參照了 Issue 編號?
- [ ] PR 描述是否清楚說明變更了什麼、為什麼變更?
- [ ] 貢獻者是否勾選了 PR 範本中的相關項目?
- [ ] 是否有測試?(UI 變更)是否有截圖?

**警訊(可能需要關閉 PR):**
- 非小型變更卻沒有對應的已核准 Issue(小型且明顯的修正不在此限;規模較大的 PR 應改為草稿,等待想法走過 Discussion 或錯誤走過 Issue 分流)
- Issue 沒有指派給該貢獻者
- PR 試圖同時解決多個不相關的問題
- 未經討論就引入 Breaking changes
- 與專案願景衝突

### 程式碼審查流程

**1. 高層次審查**

- 這個做法是否符合我們的架構?
- 這個解法的範圍是否恰當?
- 是否有更簡單的替代方案?
- 是否符合我們的設計原則?

**2. 程式碼品質審查**

Python:
- [ ] 遵循 PEP 8
- [ ] 有型別提示(type hints)
- [ ] 有 docstring
- [ ] 有妥善的錯誤處理
- [ ] 沒有安全漏洞

TypeScript/前端:
- [ ] 遵循 TypeScript 最佳實踐
- [ ] 元件結構恰當
- [ ] 正式程式碼中沒有殘留 console.log
- [ ] UI 元件具備無障礙(accessible)特性

**3. 測試審查**

- [ ] 有適當的測試涵蓋範圍
- [ ] 測試是有意義的(不只是為了衝測試涵蓋率)
- [ ] 測試在本機與 CI 上都能通過
- [ ] 邊界情況(edge cases)有被測試到

**4. 文件審查**

- [ ] 程式碼有適當的註解
- [ ] 複雜邏輯有說明
- [ ] 使用者相關文件已更新(如適用)
- [ ] API 文件已更新(如 API 有變更)
- [ ] 若為 Breaking change,提供了遷移指南

### 提供回饋

**正面回饋**(很重要!):
```markdown
感謝你的這個 PR!我很喜歡[他們做得好的具體地方]。

[需要變更之處的回饋]
```

**要求變更:**
```markdown
這是個很好的開始!有幾件事需要處理:

1. **[高層次的疑慮]**:[說明與建議做法]
2. **[程式碼品質問題]**:[具體範例與修法]
3. **[測試缺口]**:[需要涵蓋哪些情境]

如果對這些有任何疑問,歡迎告訴我!
```

**建議替代做法:**
```markdown
我很感謝你在這上面付出的努力!不過,我對[具體問題]有些疑慮。

你有考慮過[替代做法]嗎?這可能會更好,因為[理由]。

你覺得呢?
```

## 合併 PR 批次

在不互相干擾的情況下,把一批已核准的 PR 合併進來的具體做法:

- **一律使用 squash-merge。**每個 PR 一個 commit,可以讓 `main` 保持線性,也讓還原變更變得容易。
- **預期 CHANGELOG 會衝突。**每個 PR 都會在 `[Unreleased]` 底下新增一個項目,所以第 N 個合併常常會讓其他 sibling PR 變成 DIRTY 狀態。解法是把該分支 rebase 到 `main` 上,並**保留雙方**的項目——它們是各自獨立的條目,不是互相競爭的編輯——接著執行 `git push --force-with-lease`。
- **貢獻者的 fork:**把 fork 的分支 rebase 到 `origin/main` 上,略過已經在上游存在的 commit,並使用明確指定 OID 的 lease 來 push:`git push --force-with-lease=<branch>:<headOID>`。只要貢獻者保留了「Allow edits by maintainers」(maintainerCanModify)選項,這個做法就能用。
- **先確認是否有排定要被取代的程式碼。**在把一個修正合併進即將被取代的程式碼之前(例如資料庫層正在遷移到 surreal-basics,issue #1031),應該把修正改導向上游,或在追蹤用的 issue 上註記,而不是合併進即將消失的程式碼中。
- **找找看是否有競爭的 PR。**合併一個修正之前,先在開放中的 PR 裡搜尋是否有其他人也在處理同一個錯誤——挑出最好的那一個合併,其餘的附上連結後關閉,而不是看到誰先審查就合併誰。

## 常見情境

### 情境 1:程式碼寫得好,但做法不對

**情況**:貢獻者寫出了高品質的程式碼,但解決問題的方式不符合我們的架構。

**回應:**
```markdown
感謝你的這個 PR!程式碼品質很好,看得出來你花了不少心思。

不過,我對這個做法有些疑慮[具體的架構疑慮]。在我們的架構中,我們[說明我們遵循的模式]。

你願意把它重構成[建議的做法]嗎?我很樂意提供具體的指引。

或者,如果你沒有時間重構,我可以接手完成(當然會註明你的貢獻)。

讓我知道你比較想怎麼做!
```

### 情境 2:PR 沒有對應指派的 Issue

**情況**:貢獻者提交了一個非小型的 PR,卻沒有已核准且已指派的 Issue。

**回應:**
```markdown
感謝這個 PR!很感謝你願意花時間貢獻。

不過,為了維持專案的一致性,我們要求非小型的 PR 必須連結到一個已核准且已指派給貢獻者的 Issue。小型且明顯的修正不在此限。這在我們的[貢獻指南](contributing.zh.md)中有說明。

這麼做可以幫助我們:
- 確保工作方向符合專案願景
- 避免重複的工作
- 在實作前先討論做法

可以請你:
1. 把這個 PR 標記為草稿(draft)
2. 如果這是功能/設計提案,開一個 Discussion;如果是修復可重現的錯誤,開一個 Issue
3. 等待一個已核准且已界定範圍的 Issue
4. 之後我們就可以繼續處理這個 PR

造成不便深感抱歉——這個流程能幫助我們更有效地管理專案。
```

### 情境 3:Idea Discussion 與願景不符

**情況**:立意良好的功能,但不符合專案目標。

**回應:**
```markdown
感謝你的建議!我能理解這對[具體使用情境]會很有幫助。

在對照我們的[願景與原則](https://github.com/lfnovo/open-notebook/blob/main/VISION.md)審視之後,我們決定不將這個功能納入核心專案,因為[具體原因——例如「這與我們的『簡潔優於功能』原則相衝突」或「這需要與我們隱私優先做法相衝突的相依套件」]。

一些替代方案:
- [如適用] 這可以做成外掛/擴充功能
- [如適用] 這個功能或許可以透過[既有功能]達成
- [如適用] 你可能會對[其他工具]有興趣,它就是為這個使用情境設計的

我們感謝你的貢獻,也希望你能理解。歡迎查看我們的 roadmap 或開放中的 issue,尋找其他貢獻方式!
```

### 情境 4:貢獻者收到回饋後失聯

**情況**:你已經要求變更,但貢獻者超過 2 週以上沒有回應。

**2 週後:**
```markdown
你好!想確認一下這個 PR 的狀況。你有時間處理這些回饋嗎?還是希望讓其他人接手?

不管哪種都沒關係——只是想確保這件事不會被遺忘。
```

**1 個月後仍無回應:**
```markdown
再次感謝你開始這項工作!由於一直沒有收到回覆,我現在要先關閉這個 PR。

如果你之後想重新接手,歡迎重新開啟它或建立新的 PR。或者,我會把這個 issue 標記為開放給其他人認領。

感謝你的貢獻!
```

接著:
- 關閉 PR
- 取消 Issue 的指派
- 為該 Issue 加上 `help wanted` 標籤

### 情境 5:未經討論的 Breaking Changes

**情況**:PR 引入了未經討論的 Breaking changes。

**回應:**
```markdown
感謝這個 PR!不過,我注意到這引入了 breaking changes,而這在原本的 issue 中並沒有討論過。

Breaking changes 需要:
1. 事先討論並取得同意
2. 給使用者的遷移指南
3. 棄用緩衝期(在可能的情況下)
4. 清楚記錄這項變更

我們可以先討論一下這些 breaking changes 嗎?具體來說:
- [會破壞什麼、為什麼]
- [誰會受到影響]
- [遷移路徑]

我們可能需要調整做法,以將對既有使用者的影響降到最低。
```

## 溝通範本

### 關閉一個 PR(與願景不符)


## 最佳實踐

### 保持友善與尊重

- 感謝貢獻者付出的時間與心力
- 假設對方是出於善意
- 對新手保持耐心
- 說明*為什麼*,而不只是*做什麼*

### 保持清楚與直接

- 不要讓下一步該做什麼變得模糊不清
- 具體說明需要變更的地方
- 說明架構決策的理由
- 設定清楚的期望

### 保持一致

- 對所有貢獻者套用相同的標準
- 遵循你自己定義的流程
- 為未來參考記錄下決策

### 保護專案願景

- 說「不」是可以的
- 優先考量長期可維護性
- 不要接受你無法支援的功能
- 讓專案保持聚焦

### 保持回應迅速

- 盡量在 48 小時內回應新的 Discussions 與 Issues(哪怕只是先確認收到)
- 盡量在一週內審查 PR
- 讓貢獻者隨時掌握狀態
- 關閉過期的 issue/PR,保持專案整潔

## 拿不定主意時

自問以下問題:
1. 這是否符合我們的[願景與原則](../../VISION.md)?
2. 我們能否長期維護這個功能?
3. 這對大多數使用者有益,還是只是個邊緣案例?
4. 有沒有更簡單的替代方案?
5. 兩年後我還願意支援這個功能嗎?

如果你不確定,以下做法都是可以的:
- 向其他維護者尋求意見
- 開啟或連結一個 GitHub Discussion
- 先放一放,想清楚了再做決定

---

**請記住**:好的維護工作,是在對貢獻保持開放,與保護專案願景之間取得平衡。對不符合專案方向的事情說「不」,並不代表你不友善——那是你身為專案負責任的管理者應盡的職責。
